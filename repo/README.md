# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, AI & ML Certification Program (E&ICT Academy, IIT Roorkee). The data is synthetic (produced by
`generate_data.py`); Delhivery's real records are never used. One connected pipeline answers three questions:
**how long will a parcel take** (Part B), **which parcels will miss their promise** (Part C) and
**which hubs need which playbook** (Part D). All money is in INR.

## How to run

From a fresh clone of the `main` branch, in this order:

```bash
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py       # data/modelling_table.csv + Part A outputs
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py          # regenerates models/delay_model.pkl and the other models/ files
python predict_delay.py          # outputs/new_shipment_actions.csv
```

`requirements.txt` pins pandas, numpy, scikit-learn and joblib with `==`. `models/delay_model.pkl` is regenerated by
running `python package_model.py`; the committed pickle loads reliably only on the scikit-learn version pinned in
`requirements.txt`, so if your installed versions differ, re-run `package_model.py` instead of loading the committed
pickle. Shared cleaning and feature code lives in `src/shipment_prep.py` and is imported by Part A, `package_model.py`
and `predict_delay.py`, so training and prediction use the same preprocessing.

## Data findings

Source: `outputs/part_a_checks.csv`, `part_a_delay_by_group.csv`, `part_a_correlations.csv`. The raw export has
1,224 rows; after removing 24 duplicates 1,200 shipments remain, and 278 of them are delayed (delay rate 0.2317).

1. **Service type.** Express is delayed most often: 119 of 243 parcels, a delay rate of 0.4897, against 0.2056 for
   Standard and 0.0857 for Economy.
2. **Hub tier.** The delay rate climbs steeply from Tier 1 to Tier 3: 0.0400 (16 of 400) for Tier 1, 0.2150 for Tier 2
   and 0.4400 (176 of 400) for Tier 3.
3. **Distance.** Delay rate rises with every distance band: 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for
   401-600 km and 0.8523 for 601+ km (75 of 88 parcels).
4. **Strongest correlations with `delivery_hours`** (ranked by absolute value, `delivery_hours` excluded):
   `promised_hours` 0.8372, `distance_km` 0.4013 and `n_stops` 0.3247.
5. **Log transform.** `declared_value_inr` is right-skewed (filled-column mean INR 1,533.05 versus median
   INR 1,121.50), whereas after the natural log the mean (7.0277) and median (7.0224) almost coincide.

Cleaning facts (from `part_a_checks.csv`): 12 service-type spellings collapse to 3; 5 weight sentinel rows (999 kg)
were treated as missing; medians used for filling were 314.95 km, 1.83 kg and INR 1,121.50; the IQR rule flags
1 outlier (bounds -0.7063 and 116.5238 hours); there are 0 missing cells in the features and targets.

## Model results (regression)

Source: `outputs/part_b_*.csv`. Split sizes are 840 / 180 / 180. The scaler was fitted on training rows only: the
scaled training columns have a max absolute mean of 0.0, while the scaled test columns reach 0.2187, which shows the
test rows were not used for fitting.

- **Baseline.** Predicting the training mean gives a validation R² of -0.0212 (RMSE 18.8552 hours): it explains none
  of the variation, which is the floor any model must beat.
- **Winner on validation.** Linear regression had the lowest validation RMSE, 4.8912 hours (R² 0.9313), narrowly ahead
  of gradient boosting at 4.9165 hours (R² 0.9306), random forest at 5.4680 hours and the decision tree at
  6.2796 hours. On the single test evaluation, linear regression scored RMSE 4.5235 hours and R² 0.9493.
- **Tree depth** (`part_b_tree_depth.csv`). Depth 1 is high-bias: train RMSE 11.6334 and validation RMSE 12.1324 are
  both high and close together (gap 0.4990). Unlimited depth is high-variance: train RMSE 0.0 against validation
  RMSE 7.7890 (gap 7.7890); depth 12 shows the same pattern (gap 6.0560). The best validation RMSE, 6.2796, is at
  depth 6, which is the depth used for the tree candidate.
- **Learning rate** (`part_b_gb_learning_rate.csv`). 0.1 was best (validation R² 0.9306). At 0.01 (R² 0.7127) each
  tree adds so little that 100 trees underfit: learning is too slow. At 1.0 (R² 0.8440) each step is too large and the
  boosting overshoots, so the fit is unstable and worse.
- **Cross-validation** (`part_b_cv.csv`, same `KFold` object for both, 1,020 rows). Linear regression: mean R² 0.9261
  (std 0.0048); gradient boosting: mean R² 0.9352 (std 0.0044). This ranking **disagrees** with the validation
  ranking. The gap (0.0091) is only about two standard deviations, but cross-validation scores five folds of 204
  rows each instead of one set of 180, so it is the steadier evidence. I would lean towards shipping gradient
  boosting, since it can capture non-linear effects and interactions (for example a sale-window effect that is
  larger for Express). The test set was already used once for linear regression, so gradient boosting's test
  score has not been measured and should be confirmed on fresh data before launch. If interpretability matters more
  than 0.01 R², linear regression remains a defensible choice.

## Model results (classification)

Source: `outputs/part_c_*.csv`. Stratified split: 840 / 180 / 180 rows with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "not delayed" for every parcel scores validation accuracy 0.7667 (TN 138, FN 42) but
  catches 0 of the 42 delayed parcels (recall 0). It looks decent only because 77% of parcels are on time, and it is
  useless for the task, which is finding the late ones.
- **Models at the 0.5 rule** (`part_c_models.csv`): logistic regression F1 0.8046, decision tree (depth 6) F1 0.7470
  and default random forest F1 0.7848. Every trained model has accuracy of at least 0.8833, above the baseline.
- **Noise columns.** The five bookkeeping columns together hold 0.2245 of the forest's importance across 17 columns,
  yet all five fall outside the top 7 by F-score (F-ranks 8, 12, 14, 16 and 17) and the highest noise F-score is
  4.5847. The top seven are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`,
  `rain_flag` and `sale_event_flag` (smallest F-score among them 36.7281). The forest gives noise columns a
  noticeable share because it can split on any column to memorise training rows; the univariate F-score does not.
- **SelectKBest** (`part_c_selectk.csv`). Validation F1 is 0.6988 for k=5, 0.8333 for k=7, 0.7857 for k=10, 0.8049 for
  k=12 and 0.7848 for k=17. k=5 cuts two real signals (`rain_flag`, `sale_event_flag`) and loses a lot; k=7 keeps
  exactly the signal columns and is best; adding more columns after that only adds noise columns. The curve is not
  perfectly smooth, which hints at how noisy a 180-row validation set is. From here k = 7.
- **Tuning** (`part_c_tuning.csv`). Grid search (27 candidates, 135 fits) reached CV accuracy 0.8952 and validation F1
  0.7750; randomized search (9 candidates, 45 fits) reached 0.8905 and 0.7848; the untuned forest on the same
  7 columns reached validation F1 0.8333. Tuning therefore did **not** beat the untuned forest on validation. With
  only 42 delayed validation parcels, a handful of parcels moves F1 by several points, so the differences between
  these three rows are within noise and the tuned parameters cannot be trusted to be better. The default forest was
  chosen by the documented rule (`part_c_final_config.csv`: `default_forest_same_7_features`).
- **Threshold** (`part_c_thresholds.csv`). The rule is the highest threshold with validation recall of at least
  0.80. Recall is 0.8333 at 0.5 and 0.7619 at 0.6, so the chosen threshold is **0.5**. At 0.5 validation precision is
  0.7955 and recall 0.8333; lowering to 0.1 would lift recall to 0.9762 but precision would fall to 0.4824, i.e.
  many more unnecessary calls.
- **Test result** (`part_c_final_test.csv`, scored once at 0.5): precision 0.6889, recall 0.7561, F1 0.7209
  (TP 31, FP 14, FN 10, TN 125, accuracy 0.8667). Test recall is below the 0.8333 seen on validation and below the
  0.80 target. With only 41 delayed parcels one parcel is worth about 2.4 points of recall, so the gap is about
  3 parcels, which is consistent with chance. Still, the honest reading is that the real recall is probably
  somewhat below the 0.80 target.

## Operations recommendation

Source: `hub_profile.csv`, `segment_profile.csv`, `hub_segments.csv`, `tier_vs_segment_mismatch.csv`,
`part_d_separation.csv`, `part_c_final_test.csv`, `new_shipment_actions.csv`.

- **Escalate segment** (9 hubs, segment delay rate 0.4600, mean delivery 64.6504 hours, mean distance 470.4757 km):
  Nagpur (HUB13, 0.4600), Kochi (HUB15, 0.3600), Patna (HUB17, 0.4600), Ranchi (HUB18, 0.3800), Guwahati
  (HUB19, 0.6200), Raipur (HUB20, 0.4800), Bhubaneswar (HUB21, 0.4000), Siliguri (HUB23, 0.4400) and Agartala
  (HUB24, 0.5400). The other segments are Standard (7 hubs, delay rate 0.0257) and Watch (8 hubs, 0.1550).
- **Hubs whose tier label misleads** (`tier_vs_segment_mismatch.csv`): Kolkata HUB07 is labelled Tier 1 but behaves
  like a Watch hub (delay rate 0.1400); Nagpur HUB13 and Kochi HUB15 are labelled Tier 2 but behave like Escalate hubs;
  Dehradun HUB22 is labelled Tier 3 but behaves like a Watch hub (delay rate 0.2000). The tier label should not be used
  to choose a playbook for these four; use the behavioural segment, and review the tier labels themselves.
- **Alert threshold** 0.5. On the test set, about 7 of every 10 flagged parcels are really delayed (precision
  0.6889) and about 8 of every 10 delayed parcels are caught (recall 0.7561).
- **New parcels.** 8 of the 48 new parcels were flagged; 6 of those are at Escalate hubs and need a hub-manager
  escalation, the other 2 get a proactive customer call.
- **Why K = 3.** The across/within ratio rises with K (2.8940 for K=2, 5.3928 for K=3, 6.3047 for K=4, 6.8866 for
  K=5), but that happens mechanically as clusters are split. The largest jump is from 2 to 3; after that the gains
  shrink, and the K=4 solution (cluster sizes 8-7-5-4) and K=5 solution (8-7-4-3-2) each contain a cluster of fewer
  than 6 hubs, too small to carry its own playbook. Operations also runs exactly three playbooks, so K = 3 is kept.

## Production plan

**(a) Production-readiness mapped to the repository**

| Characteristic | Where it lives |
|---|---|
| Accuracy | Held-out validation and test evidence in `part_b_metrics.csv`, `part_c_models.csv`, `part_c_final_test.csv` |
| Reproducibility | Fixed `random_state` values, pinned `requirements.txt`, generator committed verbatim, run order in "How to run" |
| Consistency | One `src/shipment_prep.py` used for training and for `predict_delay.py`; `feature_order.csv` fixes column order; stored medians in `impute_values.csv` |
| Reliability | `part_d_reload_check.csv` (reload difference 0.0); cleaning handles gaps, case/spacing variants and the weight sentinel without raising |
| Maintainability | Small single-purpose scripts, shared module, constants (`FEATURES`, `PROMISED_HOURS`) defined once |
| Performance | `predict_delay.py` scored the 48 new parcels, including loading the model, in about 1.3 seconds on the build machine (small forest on 7 selected features) |

**(b) Quantities to monitor (proposed triggers)**

1. Weekly delayed share of delivered parcels: the historical rate is 0.2317. Trigger if it moves more than 5 percentage
   points from the matching historical figure for the same kind of week.
2. Weekly share of parcels flagged: about 0.24 to 0.25 on validation and test at threshold 0.5. Trigger if it leaves
   the range 0.15 to 0.35.
3. Recall on parcels whose outcome is now known (rolling 4 weeks, at least 30 delayed parcels): test recall was
   0.7561. Trigger a review if it falls below 0.65.
4. Input drift: weekly mean `distance_km` and share of Express parcels versus the training table; trigger if either
   shifts by more than 10 percent.

**(c) Retraining and the sale window.** Retrain monthly on the latest delivered parcels and immediately when any
trigger above fires. The 15-28 September sale window (`sale_event_flag`) should be compared against the same kind of
event (last year's sale window or the previous sale), not against ordinary weeks, because sale parcels are slower by
design, especially Express. Data drift here would look like longer lane distances, more stops per route, a different
mix of service types, new or re-tiered hubs, or a change in how often rain or sales occur.

## Limitations

1. **Synthetic data.** Relationships were generated by a formula, so results (including the very high R²) will not
   transfer to real Delhivery operations without re-validation.
2. **Small test set.** The test set has 41 delayed parcels, so precision, recall and F1 are imprecise; one parcel
   changes recall by about 2.4 points.
3. **Threshold tuned on one validation split.** The threshold and the choice between the three forest configurations
   rest on 180 validation rows (42 delayed), and the three configurations differ by amounts inside that noise.
4. **Random split.** Parcels were split at random rather than by time, so the test result may be optimistic compared
   with predicting genuinely future weeks. Hub segments were built from the same historical parcels used for training.
5. **Segmentation scale.** K-Means is run on only 24 hubs, so segment boundaries are sensitive to a single hub moving.
